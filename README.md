# Automated Compliance Audit & Intent Classification Engine

A deterministic, 100% rule-based (zero ML) pipeline that ingests raw UK
customer interaction transcripts, masks PII under UK GDPR before any
analytical processing, classifies intent against a hierarchical JSON
taxonomy, computes an auditable Compliance Risk Score, and loads
everything into a SQL warehouse that powers a compliance dashboard and
an auditor work queue.

Built against the *Corporate Digital Transformation: Automated
Compliance Audit & Intent Classification Engine* candidate assessment
brief (2-week sprint, UK Financial Services / Utilities / Telco /
Healthcare scope, FCA Consumer Duty + UK GDPR).

## Why deterministic, not ML

Per the brief: regulated UK institutions need an auditable, explainable
link between a flagged interaction and the exact rule/phrase that fired
it, zero hallucination risk, and instant governance updates via config
changes rather than model retraining. Every score in this project
traces back to a named `rule_id` in `rule_matches` - there is no
statistical model anywhere in the pipeline.

## Pipeline (brief Section 2.1)

```
CSV (5,000 raw interactions)
        │
        ▼
 1. Raw Ingestion         pandas reads the source file
        │
        ▼
 2. PII Masking Gate      src/pii_scrubber.py  -- masks NI numbers, cards,
        │                 phones, emails, postcodes BEFORE anything is
        │                 written anywhere (config/pii_patterns.json)
        ▼
 3. Taxonomy Matching     src/rule_classifier.py against MASKED text
        │                 (config/rules_config.json)
        ▼
 4. Risk Scoring Matrix   base weight + modifiers (+ repeat-escalation
        │                 in a second pass once all rows are loaded)
        ▼
 5. SQL Warehouse Load    src/etl_pipeline.py -- idempotent inserts into
        │                 the schema built by sql/00_schema_ddl.sql
        ▼
 6. BI Reporting          dashboard/app.py (Streamlit) + sql/01..12
```

## Quickstart

```bash
pip install -r requirements.txt

# Build the schema and load the sample dataset (idempotent - safe to re-run)
python src/etl_pipeline.py

# Run any of the 12 analytical queries
python src/run_sql.py sql/01_daily_compliance_breach_summary.sql
python src/run_sql.py sql/11_pii_assurance_check.sql   # should print "0 row(s)"

# Launch the dashboard
streamlit run dashboard/app.py

# Run the test suite (>90% coverage on the core pipeline modules)
pytest tests/ --cov=src --cov-report=term-missing
```

To point at PostgreSQL 15+ instead of the default local SQLite file,
set `DATABASE_URL` (e.g. `postgresql+psycopg2://user:pass@host/db`)
before running `etl_pipeline.py`, `run_sql.py`, or the dashboard -
nothing else needs to change. `sql/00_schema_ddl.sql` executes
unmodified on both engines; a handful of the analytical queries use one
SQLite-specific date/time function each (called out with a Postgres
equivalent in that file's header comment) since the project is
delivered and CI-tested against SQLite for a zero-setup reviewer
experience.

## Design decisions

**Two real bugs found in the brief's own worked patterns, fixed and
regression-tested.** Building `sql/11_pii_assurance_check.sql` (the
brief's own required "expect zero rows" check) against the loaded data
caught two gaps in the literal regex patterns given in Section 3.1:

1. The NI-number pattern's letter class excludes `Q`, so it would have
   *missed* the brief's own worked example, `QQ123456C` - which is the
   standard HMRC-documented placeholder NINO, used precisely because it
   can never be issued to a real person. Fixed by widening the letter
   class (see the `description` field in `config/pii_patterns.json`).
2. The card-number pattern is capped at 16 digits with a trailing `\b`
   anchor. Because `\b` can only match at the *true* end of a digit
   run, a quantifier capped below the run's actual length can never
   match at all - so any card-shaped token longer than 16 digits (the
   sample data contains 36 examples of 19-digit tokens) was left
   completely unmasked. Widened to 19 digits.

Given the brief's own KPI is 0% PII leakage, both fixes err toward
over-masking rather than under-masking. Both are covered by regression
tests in `tests/test_pii_scrubber.py::TestKnownGapsFixedDuringBuild`,
and `sql/11_pii_assurance_check.sql` now returns zero rows against the
full loaded dataset.

**Two-layer load: staging + clean fact table.** `stg_raw_interactions`
keeps one row per SOURCE row (duplicates, blanks, bad timestamps and
all) so `sql/10_data_quality_report.sql` has real source-quality
signal to report on. `interactions` is the deduplicated, canonicalised
fact grain everything else joins against. **Both tables only ever store
already-masked text** - `PIIScrubber.scrub()` runs in Python before
either table receives a single INSERT, so raw unmasked text never
touches disk anywhere, satisfying the brief's zero-PII-persistence
requirement even at the staging layer.

**No AUTOINCREMENT/SERIAL anywhere in the schema.** Every primary key
is either a natural key from the source (`interaction_id`), a
deterministic composite key (`(interaction_id, rule_id)` on
`rule_matches`), or an application-assigned integer
(`stg_raw_interactions.stg_row_id`). This is what makes
`sql/00_schema_ddl.sql` execute completely unmodified on both SQLite
and PostgreSQL - no `IF`/`ELSE` dialect branching needed in the DDL.

**Primary category = highest-weight match, not summed.** Text can
match keywords from more than one base category (e.g. both "cannot
afford" and "overcharged" in one message). Rather than stacking base
weights uncapped, the highest-weight matching category becomes the
`primary_category` and only its weight enters the score; every
category that matched (not just the primary one) is still written to
`rule_matches`, so no signal is lost for `sql/06_rule_effectiveness_report.sql`
or for audit purposes - only the scoring formula avoids double-counting.

**`flag_actions` review/action timestamps are synthesized.** The brief
provides no ground-truth data for when a flagged interaction was
actually reviewed or actioned, but `SQL-04` (SLA tracking) and `SQL-05`
(auditor queue) both need that lifecycle to mean anything.
`src/etl_pipeline.py::_synthesize_flag_action` generates a
deterministic (seeded by `interaction_id`, so idempotent reruns are
byte-identical), documented distribution: ~75% of flags are reviewed,
of which ~80% land inside their SLA window and ~20% breach it. This is
clearly a stand-in for real operational data, not a claim about actual
review performance.


**Repeat-escalation is implemented and tested, but doesn't fire on the
supplied sample.** `MOD-REPEAT` (+15 points for a customer's 3rd+
flagged interaction within a rolling 7 days) is applied in a dedicated
post-load pass (`apply_repeat_escalation`) using the exact same
rolling-window logic as `sql/03_repeat_escalation_detection.sql`. The
supplied 5,000-row dataset happens to spread each repeat customer's
interactions weeks or months apart, so neither the SQL query nor the
scoring modifier finds a qualifying case on this particular file - that
is a genuine, correct result, not a bug. `tests/test_repeat_escalation.py`
proves the logic itself works correctly using synthetic close-together
timestamps (including a case where the bonus pushes an interaction from
Medium into High tier, and an idempotency check).

**Data cleaning rules.** Channel values (11 raw spelling/casing
variants observed, e.g. `CALL`, `call_transcript`, `Call Transcript`)
are canonicalised to `call` / `email` / `webchat` / `unknown`.
Timestamps arrive in two formats - `DD/MM/YYYY HH:MM` (the majority)
and 10-digit Unix epoch seconds (227 rows) - both are parsed; anything
else (139 rows: blank/garbage) is rejected from the clean fact table
but kept in staging with `timestamp_valid = FALSE` for the data-quality
report. Duplicate `interaction_id`s (150 in the source) are resolved by
preferring the row without the synthetic `[DUPLICATE SUBMISSION]`
marker, then the earliest timestamp.

## Testing

70 tests across 4 files, 95% coverage on the core pipeline modules
(`src/run_sql.py`, a thin CLI convenience wrapper, and `if __name__ ==
"__main__"` demo blocks are excluded from the coverage target via
`.coveragerc` - see that file for the exact scope):

- **PII scrubbing tests** - all 5 entity types against the brief's own
  worked examples, the two regression cases above, multi-entity
  messages, and boundary/edge cases (empty text, `None`, non-English
  strings, SQL-injection-shaped text, multi-kilobyte transcripts).
- **Deterministic scoring tests** - exact rule IDs and cumulative score
  math for every base category and modifier, tier boundaries, and the
  brief's own worked example (formal complaint + FCA mention = 80,
  High).
- **Repeat-escalation tests** - synthetic proof the modifier and
  re-tiering logic work correctly (see above).
- **ETL tests** - timestamp parsing (both formats + garbage), channel
  canonicalisation (all 11 observed variants), dedup rule precedence,
  and a full idempotent-rerun proof against a temp SQLite database.

## Known limitations / what I'd do with more time

- The agent-exposure and SLA reports would benefit from a real
  operational events table instead of the documented synthetic
  `flag_actions` timestamps.
- `sql/00_schema_ddl.sql` is verified against SQLite in CI; the
  PostgreSQL 15+ path is written to the same ANSI-SQL subset and
  exercised manually, but isn't part of the automated pipeline here.
- Power BI was not used for the dashboard layer - Streamlit was chosen
  instead (also explicitly permitted by the brief's tech-stack table)
  so the whole project runs end-to-end from the command line with no
  proprietary software or manual click-through setup required to
  review it.
